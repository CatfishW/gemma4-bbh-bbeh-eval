# Two-GPU implementation pilot

This exploratory study runs the branch on the existing local Gemma 4 E2B BF16
checkpoint. It is a one-seed, short-context implementation pilot, with 12 updates
per arm, not a full benchmark or a compute-matched claim about CRAFT superiority.

The preparation command selects the first four alphabetically sorted training
tasks per benchmark whose maximum calibration question length is at most 600
tokens. The original every-fourth-task holdout remains excluded from training.
Up to two eligible heldout tasks per benchmark are included in evaluation.
Selection uses names and calibration lengths, not accuracy. All 25 calibration
rows per selected training task are available to the sampler; validation uses
indices 25–28. No index >=50 is loaded by the pilot. Context checks fail rather
than silently skip examples. The selected cohort contains 300 training rows and
68 validation rows, including 20 validation rows from five heldout task families.
This family holdout is relative to this training run, not a claim that these
benchmarks have never been examined in previous repository studies.

Both arms use rank 32/alpha 64 LoRA, 4 roots per update, 2 samples per arm,
32/96/32 prefix/continuation/answer token caps, temperature 0.8, gate temperature
1.0, learning rate 2e-5, and seed 20260904. Context is capped at 2048 tokens.
The 20,000-token safety ceiling cannot bind before 12 full updates (worst case
16,896 sampled tokens). The only algorithm difference is the suffix baseline:
cross-fitted siblings for `full`, historical prompt return for `no_crossfit`.
Both use the explicitly configured 0.4 accuracy floor, not a calibrated estimate
of base accuracy. Equal updates do not imply equal sampled tokens or GPU work.

The six prespecified validation conditions are each adapter and the untrained
adapter, each using the stochastic gate and forced continuation. Checkpoint 12
is used without validation checkpoint selection. An initial synthetic 2+2 GPU
probe showed a strongly saturated stop gate; probability and forced-continuation
controls were therefore declared before benchmark outcomes were examined.

```bash
PY=/data/benwulab/gemma4-rl/env/bin/python
OUT=/data/benwulab/gemma4-rl/craft-20260905/pilot
$PY scripts/craft_pilot.py prepare \
  --datasets-root /data/benwulab/gemma4-eval/datasets \
  --model-path /data/models/gemma-4-E2B-it --output "$OUT"

# Run concurrently in separate terminals; each child sees one logical GPU.
CUDA_VISIBLE_DEVICES=0 OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  $PY -u scripts/craft_pilot.py worker --arm full --output "$OUT"
CUDA_VISIBLE_DEVICES=1 OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  $PY -u scripts/craft_pilot.py worker --arm no_crossfit --output "$OUT"

# Requires all six complete, exactly matched prediction files.
$PY scripts/craft_pilot.py report --output "$OUT"
```

Training checkpoints preserve optimizer, scheduler, RNG and LoRA state with
integrity hashes. Each worker exits on a failed subprocess and writes its
completion marker only after its entire lane finishes. Individual training
commands support the existing exact-protocol `--resume`; the worker itself does
not resume an existing run or overwrite any result. Per-example evaluation
predictions are flushed to disk, but an interrupted evaluation is incomplete
until rerun to a fresh output directory.

Raw benchmark questions, traces, predictions, model weights and optimizer files
stay in the remote experiment directory. Commit only aggregate results. The
report checks exact key sets, rejects duplicates and incomplete runs, separates
seen and heldout task counts, and reports paired wins/losses, exact McNemar p and
a task-stratified bootstrap interval. The interval conditions on these selected
tasks; it does not quantify uncertainty over new task families or training seeds.

GPU memory telemetry measures this process's PyTorch allocations. Both physical
GPUs also host existing services, so elapsed times are shared-machine observations,
not isolated latency claims. Step wall time excludes model loading, checkpoint
writing and the six evaluations; these must not be described as free compute.
